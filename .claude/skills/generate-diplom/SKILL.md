# Generate Diplom — генерація кваліфікаційної роботи за правилами «Одеської політехніки»

Генерує текст дипломної (кваліфікаційної) роботи, який **за побудовою**
відповідає офіційним правилам оформлення і повторює структуру, глибину
й академічний стиль захищеного еталона. Мета — не «накидати текст», а
видати розділ/роботу, що **проходить `/grill-diploma` без BLOCKER/MAJOR**.

## Вхід

Аргумент — що генерувати:
- конкретний елемент: `вступ`, `розділ 3`, `анотація`, `висновки`, `розділ 2.4`;
- `повна робота` — згенерувати скелет усіх структурних елементів по черзі;
- порожньо — запитати у користувача тему, рівень (бакалавр/магістр),
  спеціальність/ОПП, керівника, групу, перелік розділів. **Не вгадувати.**

Перед генерацією зібрати відсутні метадані титулу через `AskUserQuestion`
(тема, ПІБ здобувача, група, спеціальність, ОПП, керівник зі ступенем і
званням, місто, рік) — без них титул і анотацію коректно не оформити.

## Джерела істини (читати перед генерацією)

1. **`docs/diploma-rules/RULES.md`** — нормативні правила оформлення.
   Це **тверді обмеження**, не рекомендації. Кожна числова константа
   (TNR 14 пт, інтервал 1,5, поля 25/10/20/20, абзац 1,25 см, кеглі
   титулу 12/14/16, відступи змісту 0/0,5/1,25 тощо) — обов'язкова.
2. **`docs/diploma-rules/references/sample-work.pdf`** + `sample-work.txt`
   та `references/README.md` — **зразок, що наслідувати**: розбиття на
   розділи (вимоги → планування → алгоритм → проєктування → реалізація →
   тестування → експлуатація), наявність «Висновки до розділу N» після
   кожного розділу, академічний тон, спосіб подачі вимог/алгоритмів/таблиць,
   пропорції обсягу (основна частина ~70–75 с., 10–15 джерел, додатки).
3. **`docs/diploma-rules/appendices/*.docx`** — еталонне оформлення
   титулу, анотацій (укр + ABSTRACT), змісту, вступу.

За розбіжності RULES.md (як оформити) має перевагу; еталон визначає
**що писати і наскільки глибоко**, а не нормативні параметри.

## Процедура

### 1. Підготовка
- Прочитати `RULES.md` повністю.
- Прочитати `references/README.md`; за потреби — відповідні фрагменти
  `sample-work.txt` (grep по назві елемента: `ЗМІСТ`, `ВСТУП`,
  `Висновки до розділу`, назва розділу) як зразок глибини й стилю.
- Звірити структуру цільової роботи з еталонною; відсутні розділи —
  узгодити з користувачем, не додавати «від себе» мовчки.

### 2. Генерація (по структурних елементах, кожен — окремо)
Дотримуватися порядку §2.1 RULES.md: титул → анотація укр → ABSTRACT →
зміст → перелік позначень (за наявності) → вступ → розділи (кожен з
«Висновки до розділу N») → загальні висновки → список джерел → додатки.
Кожен елемент — з нової сторінки.

Під час написання застосовувати правила як інваріанти, зокрема:
- заголовки структурних елементів — ВЕЛИКИМИ, по центру, без крапки,
  без слова «розділ» (`1 НАЗВА`); додатки — дозволені літери (не Ґ Є З І Ї Й О Ч Щ Ь);
- нумерація підрозділів/пунктів `1.1`, `1.1.1` без крапки після номера;
- на **кожен** рисунок/таблицю/сценарій/лістинг/нумеровану формулу —
  посилання в тексті (`рис. 3.1`, `табл. 2.3`, `(2.1)`) **до** появи об'єкта;
- підпис рисунка під ним по центру `Рисунок N – назва` (мала літера, без крапки);
  заголовок таблиці над нею `Таблиця N – назва`; нумерація в межах розділу;
- переліки: двокрапка перед, `;` між позиціями, `.` остання, схема
  цифра→літера→тире, права дужка `)`;
- формули — окремим рядком по центру, блок «де» з познакою на 1,25 см;
  жодних сканованих формул (генерувати як текст/LaTeX);
- список джерел — у порядку першої згадки, ДСТУ 8302:2015, з `(дата
  звернення: РРРР-ММ-ДД)` для електронних; дати скрізь ISO 8601;
- анотація: бібліоопис → обсяг елементів → результати → `Ключові слова:`/`Keywords:` курсивом;
- вступ: актуальність; мета і задачі; об'єкт; предмет; апробація —
  назва позиції напівжирним з крапкою, далі текст у тому ж рядку;
- стиль — академічний, безособовий, термінологічно послідовний;
  глибина абзаців і таблиць — як в еталоні, не «вода».

### 3. Формат виводу
- За замовчуванням писати у Markdown-файли в робочу теку (узгодити шлях;
  типово `thesis/<slug>.md`), один файл на структурний елемент або один
  зведений — за бажанням користувача.
- Markdown не несе мм/кеглів/інтервалів: для кожного згенерованого
  елемента додати в кінці блок `<!-- ОФОРМЛЕННЯ: ... -->` із вимогами,
  які виконуються вже у Word/LaTeX (поля, кеглі титулу, відступи змісту,
  Courier New 10 пт для лістингів тощо), щоб ручне форматування було
  однозначним. Це і є «потребує ручної перевірки» з боку генерації.

### 4. Очищення тексту від AI-ознак (обов'язково)
Кожен згенерований прозовий фрагмент (вступ, тіло розділів, висновки,
анотація, описи) **перед самоперевіркою** прогнати через скіл
**`humanizer`** — прибрати ознаки AI-письма: роздуті формулювання,
«rule of three», AI-лексику, надлишкові тире, негативні паралелізми,
пасив, filler-фрази. Текст має читатися як написаний людиною в
академічному регістрі, не втрачаючи термінологічної точності й
відповідності RULES.md. Не «гуманізувати» структурні константи
(нумерацію, підписи `Рисунок N – …`, формули, бібліоописи) — лише прозу.

### 5. Самоперевірка (обов'язково)
Після генерації будь-якого елемента прогнати його через **`/grill-diploma`**
(передати шлях до згенерованого файлу). Якщо звіт містить BLOCKER або
MAJOR — виправити і перегенерувати, доки вердикт не стане
`PASS` / `PASS WITH FIXES` без BLOCKER/MAJOR. Лише тоді повідомляти готовність.

## Принципи
- **Правила — не побажання.** Жоден елемент не «готовий», доки текст не
  пройшов `humanizer` і `/grill-diploma` не підтвердив відсутність BLOCKER/MAJOR.
- **Еталон — для глибини й структури, RULES.md — для оформлення.**
  Не копіювати текст еталона дослівно (інша тема) — наслідувати каркас,
  рівень деталізації, академічний регістр.
- Не вигадувати фактів про неіснуючий продукт: якщо генерується робота
  під реальний проєкт цього репозиторію — брати зміст з коду/доків;
  інакше явно позначати плейсхолдери `[ПОТРЕБУЄ ДАНИХ: ...]`, а не
  фабрикувати числа/результати тестів.
- Уточнювати неоднозначне до генерації (рівень, спеціальність, перелік
  розділів), а не після.
